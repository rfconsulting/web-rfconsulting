Error 547 al crear un período contable: diagnóstico y solución en SQL Server

Un caso real sobre cómo aislamos una restricción de base de datos que impedía abrir el ejercicio 2026, corregimos el esquema con control y validamos el proceso completo.

RF ConsultingPublicado: 27 de agosto de 20269 min de lectura
Entorno técnico

Sistema: Annual Enterprise Contabilidad 9.2.1
Motor: SQL Server Advanced de 64 bits
Versión: 16.0.1000.6

Los identificadores de empresa, clientes, servidores y bases de datos fueron omitidos. Los ejemplos deben adaptarse y probarse antes de usarse.

Importante: modificar restricciones es una migración de esquema. Antes de ejecutar DDL, realiza un respaldo completo y verificado, confirma la instancia y la base de datos, y prueba el cambio fuera de producción.

El caso se presentó en Annual Enterprise Contabilidad 9.2.1, conectado a SQL Server Advanced de 64 bits, versión 16.0.1000.6. Al intentar ejecutar el precierre de 2025, la aplicación mostraba un mensaje breve: “Error: 70 — No es posible hacer el precierre”. El sistema no podía crear el período 2026 y, aunque la interfaz parecía ser el origen, la evidencia apuntó en otra dirección.

La clave fue seguir el dato desde la interfaz hasta la base: observar, reproducir, aislar una sola variable y validar nuevamente desde el flujo real.

The INSERT statement conflicted with the CHECK constraint. The conflict occurred in column 'siPeriod'.

Una restricción CHECK define qué valores acepta una columna. Es útil para proteger la integridad de los datos, pero también puede bloquear una operación válida cuando su regla queda desactualizada.

1. El síntoma: “No es posible hacer el precierre”

Para el usuario, el incidente se manifestaba únicamente mediante este mensaje de la aplicación:

Error: 70
No es posible hacer el precierre.

El aviso confirmaba que el proceso había fallado, pero no mostraba la causa técnica. Durante el precierre, la aplicación consultaba si el período 2026 existía y, al no encontrarlo, intentaba insertarlo. En ese punto, SQL Server generaba un segundo código, el error 547, e identificaba una restricción CHECK sobre la columna siPeriod.

Msg 547, Level 16
The INSERT statement conflicted with the CHECK constraint.
The conflict occurred in column 'siPeriod'.

Por tanto, el error 70 era el mensaje funcional presentado por Annual Enterprise; el error 547 era la evidencia técnica registrada en la capa de base de datos.

Una restricción CHECK define qué valores acepta una columna. Es útil para proteger la integridad de los datos, pero también puede bloquear una operación válida cuando su regla queda desactualizada.

The INSERT statement conflicted with the CHECK constraint. The conflict occurred in column 'siPeriod'.

Una restricción CHECK define qué valores acepta una columna. Es útil para proteger la integridad de los datos, pero también puede bloquear una operación válida cuando su regla queda desactualizada.

2. La traza descartó un cálculo incorrecto

La primera pregunta era sencilla: ¿la aplicación estaba calculando mal el siguiente ejercicio? La captura de actividad en SQL Server mostró que enviaba explícitamente 2026, con fechas de inicio y cierre correctas.

INSERT INTO dbo.CXXPeriods
    (siPeriod, dtStart, dtEnd, boStatus)
VALUES
    (2026, '20260101', '20261231', 1);

Al ejecutar una prueba equivalente directamente en SQL Server, el mismo error apareció. Esto separó el problema de la interfaz y concentró el diagnóstico en el esquema de la base de datos.

3. La causa raíz: un límite de año estático

La inspección del constraint reveló una regla que aceptaba períodos entre 1980 y 2025:

([siPeriod] >= (1980) AND [siPeriod] <= (2025))

La aplicación hacía lo correcto; era la base de datos la que rechazaba cualquier año posterior a 2025. Además, el modelo separaba la información de cada empresa en familias de tablas. La misma regla aparecía en 20 tablas relacionadas con períodos, meses, asientos, saldos, presupuestos y aperturas.

Corregir únicamente la tabla de períodos habría permitido el primer INSERT, pero podía trasladar el fallo al siguiente paso del proceso contable.

4. Comparar esquemas ayudó a validar la hipótesis

Otra familia de tablas dentro de la misma base operaba sin ese límite superior. La comparación mostró que aceptar años posteriores a 2025 no requería modificar claves primarias, claves foráneas, fechas del sistema ni el valor interno de versión de la base.

Esta diferencia era consistente con una plantilla de creación o una ruta de migración antigua que continuó generando una fecha máxima fija. Es una hipótesis sobre el origen histórico; la causalidad inmediata sí quedó demostrada mediante la prueba controlada.

5. Una prueba controlada antes de migrar

Primero se retiró solamente el CHECK de la tabla de períodos. Luego se repitió el INSERT dentro de una transacción y se revirtió la prueba:

BEGIN TRY
    BEGIN TRANSACTION;
    INSERT INTO dbo.CXXPeriods
        (siPeriod, dtStart, dtEnd, boStatus)
    VALUES (2026, '20260101', '20261231', 1);

    SELECT @@TRANCOUNT AS TranCount,
           XACT_STATE() AS XactState;
    ROLLBACK TRANSACTION;
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
    THROW;
END CATCH;

Antes del cambio, el alta fallaba con el error 547. Después, el mismo dato fue aceptado. Esa prueba aislada confirmó que la restricción era la causa y no una coincidencia.

6. La corrección debía cubrir el flujo completo

Con la causa confirmada, se auditaron las restricciones equivalentes de la familia afectada y se generaron sentencias DROP CONSTRAINT únicamente para las reglas cuyo contenido coincidía con el límite 1980–2025.

  • Se ejecutó primero en modo auditoría, sin cambios.
  • Se revisaron las tablas y restricciones detectadas.
  • La migración se protegió con transacción, SET XACT_ABORT ON y manejo de errores.
  • Se comprobó que no quedaran reglas de período con máximo 2025.
  • No se deshabilitaron constraints de forma global ni se modificaron PK o FK.

La auditoría total encontró 241 restricciones estáticas: 240 distribuidas entre familias empresariales y una adicional en una tabla global de bloqueos. Este último hallazgo era importante porque podía provocar un error posterior aun cuando el precierre inicial ya funcionara.

7. La prueba definitiva ocurrió en la aplicación

Una prueba SQL confirma que la base acepta el dato, pero no demuestra que todo el proceso contable funcione. Después de retirar las 20 restricciones de la familia piloto, se repitió el precierre desde el sistema.

El ejercicio 2026 fue creado y procesado correctamente. La validación cubrió así la secuencia completa: cálculo en la aplicación, envío a SQL Server, persistencia y continuación del flujo contable.

8. Qué conviene aprender de este caso

  • El mensaje exacto importa. El error 547 y el nombre del constraint dirigieron la investigación al punto correcto.
  • Reproducir fuera de la interfaz reduce variables. Si el mismo INSERT falla manualmente, la capa visual deja de ser la principal sospechosa.
  • Una fecha fija es deuda técnica. Los límites temporales deben revisarse antes de que expire su horizonte.
  • Una tabla rara vez representa todo el proceso. Hay que auditar relaciones y tablas homólogas para no desplazar el error.
  • La validación funcional cierra el diagnóstico. La solución termina cuando el usuario puede completar el flujo real.

Conclusión

El bloqueo del período 2026 no era un error de cálculo de la aplicación, sino una regla de integridad que había cumplido su fecha de vencimiento. La solución responsable no consistió en desactivar controles a ciegas: se trazó la operación, se reprodujo el fallo, se inspeccionó el esquema, se probó una modificación mínima y luego se migraron únicamente las restricciones equivalentes.

Ese recorrido convirtió un error genérico de cierre contable en una causa demostrada, una corrección acotada y un resultado verificable.
